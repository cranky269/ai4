## 3. `track(detections)` 没有图像入参 —— 两个连带影响

**现象**：`函数接口.md` 5.1 的签名是 `track(detections)`，且节点图谱里
`/visual_tracker` **只订阅 `/detections`**、不订阅图像。这会连带影响两件事：

### 3.1 GMC（全局运动补偿）无法启用

BoT-SORT 的 **GMC 需要原始图像**估计背景运动
（`boxmot` / `ultralytics` 的接口都是 `update(dets, img)`）。

**我的处理**：按文档走，守住签名与图谱 ——

- 实现**无图像版**的 BoT-SORT 核心：卡尔曼滤波 + **两阶段关联**（高分→全部航迹；
  低分→未匹配航迹）+ 贪心 IoU 匹配；
- ReID 关闭、**GMC 关闭**，只留一个可插拔钩子 `set_gmc()`（将来要开不必重构）。

依据 `拆解文档` 第九章第 3 条：
> GMC 列为可选优化项；**若不上 BoT-SORT，纯 SORT 即可**。

### 3.2 `area_ratio` 的画面尺寸从哪来

`VisualTrack.area_ratio = bbox 面积 / 画面总面积`，但签名里**既没有图像、
也没有画面尺寸**，按签名**算不出来**。

**我的处理**（**不改签名**）：画面尺寸做成模块级常量 + 可注入。

```python
# lib/visual_tracker.py
DEFAULT_FRAME_SIZE = (640, 480)                 # 原则第 6 条：未指定参数做成模块级常量

setup(track_buffer=30, frame_size=(640, 480))   # 文档签名之外的可选参数
tracker.set_frame_size(width, height)           # 需要时再注入
```

节点侧从 **ROS 参数**读 `width` / `height`，**不订阅图像**，图谱不变。

**组长的判定（2026-10-06）**：

> **允许修改成图像输入，即与模块 4（视觉检测）一样的输入类型**；
> 并且**认可 `area_ratio` 的补正方案（模块常量）**。
> 但指出我给的示例代码有两处问题：
> ① `setup(track_buffer=30, frame_size=(640, 480))` **硬编码字面量，没引用
> `DEFAULT_FRAME_SIZE` 常量**；② `tracker.set_frame_size(width, height)` 里
> **`width` / `height` 从哪来没交代**。

**已按判定完成修改**（两处批评都已处理）：

| 组长指出的问题 | 修改后 |
|---|---|
| 示例硬编码 `(640, 480)`，没引用常量 | `setup(track_buffer=30, frame_size=DEFAULT_FRAME_SIZE)` —— **引用模块常量**；节点里的 `DEFAULT_WIDTH/HEIGHT` 也改为 `DEFAULT_FRAME_SIZE[0]/[1]` |
| `width` / `height` 来源没交代 | **明确两级来源**（见下） |

签名（`image` 为可选，类型与模块 4 `detect` 的入参一致）：

```python
def track(detections: list[DetectedTarget],
          image: np.ndarray | None = None) -> list[VisualTrack]
```

**画面尺寸的两级来源（`area_ratio` 的计算基准）**：

| 优先级 | 来源 | 说明 |
|---|---|---|
| **1（优先）** | **图像入参** `track(dets, image)` | 由 `image.shape`（`(高, 宽, …)`）自动取实际尺寸并更新基准；相机换分辨率会自动适配 |
| **2（兜底）** | `setup(frame_size=...)` / `set_frame_size(w, h)` | 默认值为模块常量 `DEFAULT_FRAME_SIZE = (640, 480)`；图像尚未到达时用它 |

**节点侧**（`scripts/visual_tracker_node.py`）：

- 新增订阅 `/camera/image_raw`（参数 `~use_image`，默认 `true`；`~image_topic` 可改），
  每帧缓存最新图像并在调用核时传入；
- `~width` / `~height` 改为**兜底值**（默认取 `DEFAULT_FRAME_SIZE`）；
- 无 `cv_bridge` 或缺图像时**自动退回兜底尺寸**，不报错、不影响跟踪。

**GMC**：图像入参已具备，但属《拆解文档》第九章第 3 条的**可选优化**，
**当前仍默认关闭**，`set_gmc()` 钩子保留（见 `组长确认可优化内容.md`）。

**验证**：新增 7 个单测覆盖图像路径（含"宽高弄反"与"非法形状容错"），
并在 E2E 新增**阶段 C** —— 节点兜底尺寸写 640x480，实际发布 320x240 图像，
断言 `area_ratio` 按 **320x240** 计算（证明图像入参优先生效）。
实测：`234 passed`，三个 E2E 全 PASS（含阶段 C）。

## 4. 组长归档多处缺执行位（报备 + 建议重新打包）

解压 `ai4.tar.gz` 后有 **2 类**文件的权限位不对，**都会让同学第一次上手就卡住**。
（以下 mode 均为**直接读取 tar 内条目**所得，非解压后的推断值。）

### 4.1 `devel/_setup_util.py` 缺执行位 → ROS 环境完全加载不上

**现象**：`source catkin_ws/devel/setup.sh` 报错：

```
setup.sh: 行 61: .../devel/_setup_util.py: 权限不够
Failed to run '".../_setup_util.py"': return code 126
[rospack] Error: package 'uav_tracking' not found
```

**根因**（对比同目录其它文件）：

| 文件（tar 内） | mode | 判定 |
|---|---|---|
| `catkin_ws/devel/setup.sh` | `0755` | ✅ |
| `catkin_ws/devel/env.sh` | `0755` | ✅ |
| **`catkin_ws/devel/_setup_util.py`** | **`0644`** | ❌ **缺执行位** |

`setup.sh` 第 61 行会**执行**它 → 缺执行位则返回 126
→ `ROS_PACKAGE_PATH` 为空 → **所有包都找不到**。

**修复**：`catkin_make`（重新生成 devel，权限自动恢复）或 `chmod +x catkin_ws/devel/_setup_util.py`

### 4.2 `scripts/*.py` 缺执行位 → 三个已有 E2E 全都跑不起来

**现象**（虚拟机内**实测证据**）：

```
$ chmod 644 catkin_ws/src/uav_tracking/scripts/cluster_node.py     # 还原归档权限

[rosrun] Couldn't find executable named cluster_node.py below .../uav_tracking
[rosrun] Found the following, but they're either not files, or not executable:
[rosrun]   .../uav_tracking/scripts/cluster_node.py
```

**根因**：归档里 `scripts/*.py` **全是 `0644`**，但三个 `run_e2e.sh`
都用 `rosrun` 启动节点（如 `test/cluster/e2e_test/run_e2e.sh` 第 50 行

**全新解压后必然失败**，且报错信息（"Couldn't find executable"）**容易被误判成代码问题**。

**修复**：

```bash
chmod +x catkin_ws/src/uav_tracking/scripts/*.py
```

## 6. 类型注解写法：文档 `list[...]`，我写 `List[...]`

**现象**：`函数接口.md` 4.1 / 5.1 的签名用的是 **PEP 585 内置泛型**：

```python

```

而 Python 3.8（ROS Noetic）下 `list[Detection]` **会在函数定义时求值并抛
`TypeError: 'type' object is not subscriptable`**（内置泛型是 Python 3.9 才支持的），
除非在文件顶部加 `from __future__ import annotations`。

**我原先的说法错在哪（组长指出）**：

我写的是「依据组长既有代码 `datatypes.py` 第 23 行 `from typing import List, Tuple`，
故与组长一致用 `List[...]`」——**这个论据是错的**，因为我只看了 `datatypes.py` 一个文件。

实测组长**全部 5 个 py 文件**的注解风格：

| 文件 | `from __future__ import annotations` | 签名里用 |
|---|---|---|
| `code/cluster.py` | ✅ 第 23 行 | `list[Point3D]`（6 处） |
| `code/state_machine.py` | ✅ 第 30 行 | `list[DetectedTarget]`（6 处，如第 100 行） |
| `code/control_mux.py` | ✅ 第 24 行 | （`typing` 只用于 `Any` / `Optional`） |
| `code/config.py` | ✅ 第 20 行 | — |
| `code/datatypes.py` | ✅ 第 19/21 行 | 仅 **dataclass 字段**用 `List` / `Tuple`（dataclass 对字段注解有特殊处理） |

→ **结论与我的原说法相反**：组长主流风格是
**`from __future__ import annotations` + `list[...]`**。

**组长的判定（2026-10-06）**：

> 技术判断对，但「与组长一致」的论据反了。**要统一就应该改成 `list[...]`。**
