## 3. ⚠️ 踩到的坑（一）：组长归档**多处缺执行位**

均系**直接读取 tar 内 `mode`** 所得，非解压后推断。

### 3.1 `devel/_setup_util.py` 缺执行位 → ROS 环境完全加载不上

**现象**：`source catkin_ws/devel/setup.sh` 报错

```
setup.sh: 行 61: .../devel/_setup_util.py: 权限不够
Failed to run '".../_setup_util.py"': return code 126
[rospack] Error: package 'uav_tracking' not found
```

**根因**：`devel/setup.sh` 与 `devel/env.sh` 是 `0755`，
而 **`devel/_setup_util.py` 是 `0644`** —— 它会被 `setup.sh` **执行**，必须可执行。

**修复**：`catkin_make` 重新生成 devel 后权限自动恢复为 `0755`。

### 3.2 `scripts/*.py` 缺执行位 → 三个已有 E2E 全都起不来

**实测证据**：

```
$ chmod 644 catkin_ws/src/uav_tracking/scripts/cluster_node.py
$ rosrun uav_tracking cluster_node.py
[rosrun] Couldn't find executable named cluster_node.py below .../uav_tracking
[rosrun] Found the following, but they're either not files, or not executable:
[rosrun]   .../scripts/cluster_node.py
```

归档内 `scripts/*.py` 全为 `0644`，但三个 `run_e2e.sh` 都用 `rosrun` 启动节点
（如 `test/cluster/e2e_test/run_e2e.sh` 第 50 行）。**全新解压后 E2E 必然失败**，
且报错容易被误判成代码问题。

**修复**：`chmod +x catkin_ws/src/uav_tracking/scripts/*.py`

> 两处均已作为第 9 条报备到 `03_需群里讨论事项.md`（含建议的重打包命令），
> 并附**可能成因**：在共享文件夹 / Windows 挂载盘上打包会静默丢失可执行位。

### 7.2.3 ⚠️ 此处抓到一个真 bug：隔离曾是**静默失效**的（已修复，见 §13）

上表"隔离生效"不是一次就成的。第一版代码打出来的是：

```
[INFO] [detector] numpy 1.17.4 @ /usr/lib/python3/dist-packages/numpy   ← 隔离失效！
[ERROR] [detector] 推理失败: integer argument expected, got float
  File ".../ultralytics/data/augment.py", line 1847, in apply_image
    img = cv2.copyMakeBorder(
TypeError: integer argument expected, got float
```

**根因**：`rospy` 在 `import rospy` 时**就已经 `import numpy`**。
我原先把 `sys.path.insert(0, m4_deps)` 放在 `import rospy` **之后**、
`import numpy` **之前** —— 但 `numpy` 早已进了 `sys.modules`，再改 `sys.path` **完全无效**。
于是静默退回系统 `1.17.4`，ultralytics 的 letterbox 在这个老版本上算出 float 边界，
`cv2.copyMakeBorder` 拒收。

**修复**：把路径注入提到 `import rospy` **之前**，并加一条**会主动报错的自检**
（隔离失效直接 `logerr`，而不是只把版本打印出来）。

> **这条 bug 只有"在 ROS 里真跑"才会暴露**：单独 `python3 -c "import detector"` 时
> 没有 `rospy` 抢先导 numpy 的问题，隔离看起来完全正常。这正是"上机运行阶段"的价值。

## 10. ⚠️ 踩到的坑（二）：**M4 自身文件是 CRLF 换行**（已修复）

**这是我自己的问题，不是组长的。**

**现象**：`rosrun uav_tracking detector_node.py` 启动失败：

```
/usr/bin/env: "python3\r": 没有那个文件或目录
```

**根因**：文件是 Windows 的 `CRLF` 换行，shebang 变成 `#!/usr/bin/env python3\r`，
Linux 解析 shebang 时把 `\r` 当成解释器名字的一部分 → 找不到。

**受影响文件（8 个，均为 CRLF）**：

| 文件 | CRLF 行数 |
|---|---|
| `scripts/detector_node.py` | 241 |
| `scripts/camera_node.py` | 223 |
| `test/visual_tracker/test_visual_tracker_node.py` | 148 |
| `test/detector/test_detector_node.py` | 135 |
| `e2e_test/check_detections.py` | 124 |
| `e2e_test/check_tracks.py` | 110 |
| `e2e_test/fake_detections.py` | 94 |
| `e2e_test/fake_camera.py` | 84 |

> **为什么之前的 E2E 还能通过**：`visual_tracker_node.py` 恰好是 LF
> （它被编辑工具改写过），所以侥幸没暴露；而它自己发的 E2E 里
> `check_tracks.py` / `fake_detections.py` 是用 `python3 <路径>` 启动的，
> **不走 shebang**，因此 `\r` 不影响。

**对照组长文件**：组长**全部文件都是 LF（0 个 CRLF）** —— 这才是本仓库的既定规范。

**修复**：把 M4 新增的 **全部 26 个文件**统一转为 `LF`，并在虚拟机内复核：

```
$ file catkin_ws/src/uav_tracking/scripts/detector_node.py
Python script, UTF-8 Unicode text executable          ← 不再出现 "with CRLF line terminators"

$ head -1 .../detector_node.py | od -c | tail -2
0000000   #   !   /   u   s   r   /   b   i   n   /   e   n   v       p
0000020   y   t   h   o   n   3  \n                     ← 确认无 \r
```

**给后续同学的提醒**：在本仓库里改/建文件时**务必用 LF**，
否则 `rosrun` 会报 `python3\r: 没有那个文件或目录` 这种看起来毫无头绪的错。

### 13.1 ★ `m4_deps` 隔离**静默失效**（最重要）

详见 §7.2.3。要点：

| 项 | 内容 |
|---|---|
| 症状 | 节点打出 `numpy 1.17.4 @ /usr/lib/...`，随后每帧 `推理失败: integer argument expected, got float` |
| 根因 | `rospy` 在 `import rospy` 时**就已 `import numpy`**；我原先在 `import rospy` **之后**才改 `sys.path` —— numpy 已在 `sys.modules`，**注入完全无效** |
| 影响 | 隔离形同不存在，而且**不报错**（只是静默用系统 numpy），直到 ultralytics 内部才炸出难懂的 cv2 错误 |
| 修复 | ① 路径注入移到 `import rospy` **之前**；② 自检从"只打印版本"改为"**隔离失效直接 `logerr`**" |

修复后实测：

```
[INFO] [detector] numpy 1.21.6 @ .../lib/m4_deps/numpy（隔离生效，目录 .../lib/m4_deps）
```

> **教训**：`sys.path` 注入必须早于**任何可能间接 import 目标包的模块**，
> 只做到"在 `import numpy` 之前"是不够的。

### 13.2 E2E 画面尺寸写死 `640×480`

| 项 | 内容 |
|---|---|
| 症状 | 阶段 B 报 `FAIL: bbox 不合法（132 个）`，但样例 bbox 肉眼看着完全正常 |
| 根因 | `check_detections.py` 的越界断言用 `_frame_w/_frame_h`，而 `run_e2e.sh` 写死传 `640/480`；**`fake_camera` 给 `~image_path` 时是原样发布图片、不按 `~width/~height` 缩放**，所以实际帧是 810×1080 |
| 判定 | **不是产品 bug**：`640×1.2=768 < 805` 才被判越界，按真实 810 计算**全部合法** |
| 修复 | `run_e2e.sh` 用 OpenCV 读图片真实尺寸后再传给断言 |

### 13.3 E2E 没等 CPU 预热就断言"话题在流"

| 项 | 内容 |
|---|---|
| 症状 | 阶段 A 报 `FAIL: 话题未在流：仅 15~18 条 < 20`，而同一次运行的阶段 B 有 34 条 |
| 根因 | `/detector` 是**推理受限**的：CPU 上模型加载 + 预热期出帧只有 ~2.5~3 Hz，热后 ~5.7 Hz。原断言 `6 s / 20 条`（=3.3 Hz）正好卡在预热期 |
| 修复 | ① 启动 detector 后**固定等 20 s 预热**；② `_min_msgs` 由 20 放宽到 **5**（≈0.8 Hz）—— 该断言的本意只是"话题在流"，不是吞吐指标 |

> 为什么之前没暴露：装依赖前推理**立刻失败**，出帧反而快（10 Hz），
> `min_msgs=20` 轻松通过。**"跑得快"掩盖了"跑得对"** —— 装上真模型才显形。

## 14. 适配性与帧率实测（**组内决策依据**）

> 目的：回答「M4 能适配到什么程度」「跑得够不够快」这两个验收问题。

> 脚本：`/tmp/adapt_test.sh`（不入交付目录，需要可重建）。

### 14.1 ★ 帧率 ↔ `imgsz`（**联调整定参数**，不是"验收项"）

**测法（节点口径）**：`camera_node(_source:=image, _fps:=30)` 持续喂 810×1080 真图 →
`detector_node` 用 `yolov8n.pt` 推理 → 用 `rostopic hz /detections` 取平均。
每档先 **warmup 25 s**（CPU 上模型加载 + 线程池预热），再测 12 s。

**输入侧实测 30.067 Hz** —— 保证瓶颈在推理、不在输入。

| `imgsz` | `publish_debug` | **节点实测 FPS** | 能跟上的相机帧率 |
|---|---|---|---|
| **320** | `true` | **22.14** | ≤ 22 Hz（余量充足） |
| **320** | `false` | **22.33** | ≤ 22 Hz |
| **416** | `true` | **15.85** | ≤ 15 Hz |
| **416** | `false` | **18.11** | ≤ 18 Hz |
| **640（当前代码默认）** | `true` | **10.05** | ≤ 10 Hz |
| **640** | `false` | **10.10** | ≤ 10 Hz |

**对照：纯 `detect()` 直调（不经节点）** —— 320 → 17.9、416 → 13.7、640 → 8.6 FPS。

#### 结论

1. **`imgsz` 是"联调整定参数"，不是"是否达标"的问题。** 组长的要求是
   《函数接口.md》原话「无目标时**随相机帧率**发布空 `Detections`」——
   **"跟得上相机"即可，没有绝对 FPS 指标。**
   故：相机 ≤10 Hz → 默认 640 就够；相机 30 Hz → 传 `_imgsz:=320`（22.1 FPS）。
2. **帧率不是能力问题，是取值问题** —— 代价是远距小目标精度下降，
   **这是取舍，需团队拍板；M4 不擅自改默认值。**
3. **`publish_debug` 的影响可忽略**（320：22.14 vs 22.33；640：10.05 vs 10.10，≈1%），
   即"调试图拖慢帧率"的猜测**不成立**，无需为它做取舍。
4. **节点实测 ≥ 直调实测**（如 320：22.1 vs 17.9）。
   说明节点壳的开销（`cv_bridge` 转换、序列化、消息发布）**不构成瓶颈**。

> ⚠️ **重要提醒**：§7.4 里「节拍稳定 15 Hz、一帧不丢」是**未装模型时**的观察。
> 装上真模型后，**链路帧率 = 推理速度**，与相机帧率无关。
>
> ⚠️ 另一个曾经的误判（已由本节更正）：曾按"节点只有直调的 66%"推算 320 约 12 FPS。
> 那个 66% 来自 E2E 场景（10 Hz 假相机 + 预热不充分），**不是节点壳的开销**。

## 15. ⚠️ 踩到的坑（五）：安装脚本「装失败却报成功」（已修复）

**发现方式**：对 `install_m4_deps.sh` 做**全新安装验证**（先把 `m4_deps` 移到备份，再从头装）。

**现象**：

```
=== 3/6 ultralytics 的运行时依赖 ===
urllib3.exceptions.ProtocolError: ('Connection broken: OSError("(104, \'ECONNRESET\')")', ...)
  [OK]   运行时依赖已装          ← 网络断了，脚本却说"已装"
```

**根因**：脚本原先是

```bash
$PIP --index-url "$PYPI" "matplotlib>=3.3.0" ... 2>&1 | tail -3
ok "运行时依赖已装"          # ← 无论 pip 成败都会执行
```

管道里 **`$?` 取到的是最后一个命令（`tail`）的退出码，恒为 0**，
所以 pip 真失败了也看不见。**后果**：队友网络一抖 → 依赖装了一半 → 脚本说"装好了"
→ 之后检测报莫名其妙的错。

**修复（3 项）**：

| # | 修复 | 作用 |
|---|---|---|
| 1 | 新增 `run_pip()`：pip 输出写临时文件，`tail` 之后**返回 pip 的真实退出码** | 失败立即 `exit 1`，不再被掩盖 |
| 2 | 装完**逐包 `import` 验证**（numpy/torch/torchvision/ultralytics/matplotlib/polars/psutil/yaml/PIL/requests） | 「光看 pip 成功不算数」 |
| 3 | **网络重试**：pip `--retries 5 --timeout 60` + shell 层重试 3 次，并**保留 pip 缓存** | 实测本工程网络会 ECONNRESET；重跑不必重下 |
