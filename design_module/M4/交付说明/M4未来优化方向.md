### 1. GMC（全局运动补偿）

**是什么**：BoT-SORT 里用来估计**相机自身运动**的模块，用来抵消机身抖动带来的画面位移。
本项目是**机载相机**、抖动大，所以组长在《拆解文档》里把它列为可选优化项。

**为什么现在不做**：组长明确「别管，后期再做」。

**当前实现**：**完全关闭**，但在 `lib/visual_tracker.py` 留了可插拔钩子：

```python
tracker.set_gmc(fn)      # 后期注册一个 GMC 函数即可，主链路无需重构
```

**后期怎么做**（已具备条件）：

- `track(detections, image)` 的 **`image` 入参已经加上了**（组长 2026-10-06 批准），
  而 GMC 正好需要原始图像 → **接口已经打通，不用改签名**；
- 只需在 `set_gmc()` 里注册一个函数（如用 OpenCV 的 `calcOpticalFlowFarneback`
  或特征点法估计背景运动），把预测框做一次仿射补偿再关联。

> **结论**：GMC 是"**接线即可**"型改动，不影响现有代码结构。

### 2. 视觉帧率 / 「切换延迟 < 100 ms」口径

**是什么**：组长量化基线里有「雷达→视觉切换延迟 < 100 ms」。此前想确认
**这 100 ms 的计时起点是否包含状态机 N/M/K 帧计数**（当前 N=3），
因为那会反推视觉链需要跑多少帧率。

**为什么现在不做**：组长答复「**这个属于优化，先别做**」——即**不必现在纠结**。

#### 2.1 关于「缓冲区」（同一条答复里的要求，**已满足**）

组长同一条答复还说：「帧率未知，这个也不影响你处理……**你做个缓冲区不就得了**」。

**现状：缓冲区早已实现** —— 三个节点的订阅**全部是 `queue_size=1`（只保最新帧）**，
代码里写明了理由「图像是大消息、旧帧无意义 → 只保最新」。详见 `03` §10.1。

**为什么不做更深的缓冲**：图像消息 ≈2.6 MB，深度缓冲会让节点去算**早已过期的画面**，
**反而增加端到端延迟**，与验收要求的"平滑无卡顿"背道而驰。故**保持 `queue_size=1`**。

> 若组长本意是"深缓冲、保证一帧都不丢"，请告知，我再调整 —— **当前按现状不改**。

**当前实现与实测**（节点口径，4 核 CPU / `yolov8n.pt` / 810×1080）：

| `imgsz` | 实测 FPS | 帧周期 |
|---|---|---|
| **640（当前默认）** | 10.0 | ~100 ms |
| 416 | 15.9~18.1 | 55~63 ms |
| 320 | 22.1 | 45 ms |

**当前按"保持默认 640"处理，不改任何代码。**

**后期怎么做**（若联调发现不够快）：

- 把 `imgsz` 调小（**运行参数，改一个数字即可，不动代码**）：

  ```bash
  rosrun uav_tracking detector_node.py _imgsz:=320
  ```

- 或换有 GPU 的机器（`~device:=cuda`，参数已留）。

### 3. ReID（外观特征）

**是什么**：用目标的外观特征做跨帧匹配（人/车重识别）。

**为什么现在不做**：组长《拆解文档》原文「GMC 列为可选优化项；**若不上 BoT-SORT，纯 SORT 即可**」，
且本项目是**单目标拦截**场景，外观匹配收益小。

**当前实现**：关闭（只做 IoU 关联 + 卡尔曼滤波 + 两阶段匹配）。
