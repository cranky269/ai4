## 一、为什么要用这套脚本

M4 的节点是 ROS 节点，必须在**虚拟机**里跑。而虚拟机操作你在宿主机上看不到 ——
所以这里做了两件事：

1. **把运行过程截屏**（`证据/截图1~3`），你能直接看到虚拟机桌面上的真实画面；
2. **把运行产物落成文件**（日志、消息、带检测框的图片），你能直接打开核对。

> 所有文件都是**虚拟机里真跑出来的原始产物**，不是重新生成的示意图。

## 四、⚠️ 人工测试前必须知道的两个坑

都是这次现场调试中**真实踩到**的，不是猜的。

### 坑 1：启动顺序 —— **跟踪器必须先于状态机**

状态机在 `RADAR_GUIDE` 下对「视觉锁定」和「雷达丢失」**各自独立计数**：

```python
counters["visual_lock"] >= N(=3)  →  VISUAL_LOCK      # 视觉优先
counters["radar_lost"]  >= K(=5)  →  SEARCH/RTH
```

**本环境没有 `/radar/tracks` 的发布者**（雷达属别的模块），所以 `radar_lost` 恒为真 ——
只要状态机先起来，约 **1 秒（5 拍）就会跳 `SEARCH/RTH`**；
而 `SEARCH/RTH` **只有「雷达恢复航迹」才能回 `RADAR_GUIDE`**，一旦进去就再也出不来。

> **实测对比**：状态机比跟踪器早 7 秒启动 → 结果是 `RADAR_GUIDE -> SEARCH/RTH (visual_lock=False radar_lost=True)`，**看不到 VISUAL_LOCK**。
> 改成跟踪器先起 → `RADAR_GUIDE -> VISUAL_LOCK`。
> **这不是 M4 的 bug，是联调顺序问题**，但人工测试时极易误判。

### 坑 2：`/state` 不是周期话题

`/state` **只在状态变化时发布**（外加启动时发一次初值），**没有 latch**。
所以：

- 不能用 `rostopic echo -n 2 /state` 蹲第 2 条 —— **会永久挂住**（本次已踩）；
- 必须**先订阅 `/state`，再启动状态机与跟踪器**，才抓得到跃迁。

```bash
# 正确姿势
timeout 180 rostopic echo /state > state.txt &     # 先蹲守
# ... 再启动 state_machine_node / visual_tracker_node
```

## 七、脚本本身的取舍（如实说明）

- **`imgsz=320`**：CPU 上实测 320 约 17.9 FPS、640 只有 8.6 FPS。脚本为让验证跑得动用了 320
  —— 这是**验证脚本的取值，不是产品默认值**（产品默认仍是 640，见 `design_module/M4/交付说明/04_虚拟机实跑记录.md` §14）。
- **`conf_thres=0.4`**：默认是 0.5，这里调低是为了让测试图上 4 个目标都出来。
- **只等 25 秒预热**：CPU 首次推理较慢；机器更慢的话可把脚本里的 `sleep 25` 调大。
- **`/tmp` 里的模型与图片**：临时素材，重启会丢（见前置条件）。
