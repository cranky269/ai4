# 怎么验证 M4 是真的在跑（而不是我在编）

> 这份文档里的**每一个数字，都是我先跑出来、再写进来的**。
> 5 个方法按"省事程度"排序，**方法 1 + 方法 2 做完基本就够了**。

核心思路：**不只信一个信息源**。让「ROS 原始数据」「网页数据」「时间戳」三方互相对账，
任何一方对不上就露馅。

---

## 方法 1 · 一键自证脚本（30 秒，推荐先做）

**做什么**：虚拟机终端里粘

```bash
cd ~/m4 && bash verify.sh
```

它会自动跑 8 项交叉核对，输出 `PASS` / `FAIL`。

**我实测的输出**（`PASS=15  FAIL=0`）：

```
【核对 1】四个节点是否真的在 ROS 里注册
  [PASS] 节点存在: /camera_node
  [PASS] 节点存在: /detector
  [PASS] 节点存在: /visual_tracker
  [PASS] 节点存在: /state_machine

【核对 2】话题是否真的有发布者 / 订阅者
  [PASS] /camera/image_raw  发布者=1 订阅者=2
  [PASS] /detections  发布者=1 订阅者=3
  [PASS] /visual/tracks  发布者=1 订阅者=2
  [PASS] /state  发布者=1 订阅者=1

【核对 3】/detections 是否真的在流（实测频率）
  [PASS] /detections 在流：average rate: 10.161

【核对 4】图像是不是【现在】的（时间戳对账）
  [PASS] 最新图像时间戳距今 1 秒（是实时的，不是录像）

【核对 5】ROS 原始消息 与 网页数据 是否一致
         ROS 原始: 本帧目标数 = 4     首选框 = bbox:[8.926657..., 224.114..., 799.839..., 529.378...]
         网页数据: det_n=3  state=VISUAL_LOCK  frames=3836
  [PASS] 状态为 VISUAL_LOCK

【核对 6】画面是不是【活的】（frames 必须一直在涨）
  [PASS] 4 秒内帧数 3837 → 3878（在涨 = 真的在出新帧）

【核对 7】模型与素材是不是真的
  [PASS] yolov8n.pt 存在  6.3M  md5=95a2449609c7
  [PASS] bus.jpg 存在  136K  md5=10bd23d36a88

【核对 8】隔离依赖是否真在生效
  [PASS] detector 日志显示 numpy 隔离生效
         [INFO] ... [detector] numpy 1.21.6 @ .../lib/m4_deps/numpy（隔离生效，...）

结果： PASS=15   FAIL=0
```

**每一项在证明什么**：

| 核对 | 如果结果是"编的"，会怎样露馅 |
|---|---|
| 1 节点注册 | `rosnode list` 是 ROS master 的真实回复，编不出来 |
| 2 话题收发 | 订阅者数量是 master 里的真实连接关系 |
| 3 实测频率 | 它真的在计时收消息，10.16 Hz 是量出来的 |
| **4 时间戳** | 图像 header 的时间戳必须等于"现在"——**录像的时间戳是旧的** |
| 5 ROS vs 网页 | 两个独立来源必须一致；写死的数字对不上 |
| **6 frames 增长** | 静止画面不会增长；这是"活的"最直接的证据 |
| 7 模型 md5 | 文件是真的就能算出一致的 md5 |
| 8 依赖隔离 | 从节点自己的日志里读的 |

## 方法 2 · 断电测试（**最狠**：证明画面不是录像）

**做什么**：把"画面源头"掐掉，画面**必须立刻死**。

```bash
pkill -f camera_node
```

**我实测的**：

```
【基线】camera_node 正常：frames 4081 → 4137   （在涨 ✅）
【断电】杀掉 camera_node：frames 4145 → 4145   （**冻结** ✅）
【恢复】重新起 camera_node：frames 4195 → 4253 （又涨 ✅）
```

**为什么这条最狠**：如果网页上播的是一段**预先录好的视频**，我掐掉节点它照样播。
它**立刻冻结**，说明每一帧都是 `camera_node` 现算现发的。

**恢复**（两种都行）：

```bash
bash ~/m4/set_camera_source.sh default   # 快（约 7 秒），只重启相机
bash ~/m4/demo.sh restart                # 慢（约 60 秒），四个节点一起重启
```

## 方法 3 · 改阈值测试（证明像素真的进了模型）

**做什么**：把置信度阈值调高，**检测结果必须跟着变**。数字如果是写死的，不会理你。

```bash
CONF=0.9 bash ~/m4/demo.sh moving
```

**先看底层直调（同一张图、不同阈值）**：

| `conf_thres` | 检出目标数 | 各目标置信度 |
|---|---|---|
| 0.10 | **5** | 0.85, 0.82, 0.75, 0.64, **0.19** |
| 0.25 | 4 | 0.85, 0.82, 0.75, 0.64 |
| 0.40（默认） | 4 | 0.85, 0.82, 0.75, 0.64 |
| 0.60 | 4 | 0.85, 0.82, 0.75, 0.64 |
| **0.90** | **0** | （全被过滤） |

**再看端到端**：

```
[detector] ready: model=.../yolov8n.pt conf=0.90 imgsz=320 device=cpu ...
→ 网页： det=0  航迹=[]  state=SEARCH/RTH
```

注意这条**因果链**：阈值调高 → 检测为空 → 跟踪无航迹 → **状态机掉出锁定**。
一个写死的页面不可能跟着一起变。

**恢复**：

```bash
bash ~/m4/demo.sh moving      # 用回默认 conf=0.40
```

## 方法 4 · 换成**你自己的图**（最不可伪造）

**做什么**：把你自己的图片喂进去，看检测结果是不是跟着变。

```bash
bash ~/m4/set_camera_source.sh image /路径/你的图.jpg
```

**我实测的**：造了一张 **800×600** 的假图（和 bus.jpg 的 810×1080 明显不同）

```
启动新 camera_node: 图片 /tmp/my_own_test.png
  [INFO] [camera_node] ready: source=image fps=5.0

/camera/image_raw 的规格（跟着新源变了）：
    height: 600
    width: 800
    encoding: "bgr8"

网页数据: img_shape=[600, 800, 3]   det_n=0
```

还原成视频后：

```
    height: 1080   width: 810
网页数据: img_shape=[1080, 810, 3]   det_n=3
```

**为什么这条最不可伪造**：**图是你给的**。你拍的/你选的图出现在画面上、检测框跟着变，
我没有任何办法提前准备。

> 注意：这方法只换 `camera_node`，另外三个节点不动，所以几秒就能看到效果。

## 方法 5 · 不信网页，直接问 ROS

**做什么**：绕开网页，直接问 ROS 最底层的数据。

```bash
rostopic echo -n1 /detections      # 原始检测消息（必须有 class_id / confidence / bbox）
rostopic hz /detections            # 真实频率
rosnode list                       # 有哪些节点
rostopic info /detections          # 谁发谁收
rostopic echo -n1 --noarr /camera/image_raw   # 图像规格 + 时间戳
```

**判读**：`rostopic echo` 打出来的 bbox 数字，应该和网页左上角画面上框的位置对得上。

## 为什么这些方法伪造不了（原理）

| 方法 | 你改变了什么 | 如果是"编的"会怎样 |
|---|---|---|
| 1 自证脚本 | 什么都不改，只做交叉核对 | 三个来源对不上（时间戳尤其藏不住） |
| 2 断电 | **掐掉画面源头** | 录像会继续播；实际立刻冻结 |
| 3 改阈值 | **改模型的判定门槛** | 写死的数字纹丝不动；实际目标数 5→0、状态机掉锁 |
| 4 换图 | **换掉输入素材** | 会一直显示 bus.jpg；实际跟着变成 800×600、det=0 |
| 5 问 ROS | 绕开我做的网页 | 网页是我写的，但 ROS master 不是 |

**共同点**：这些操作都在**你手上**，而且**结果必须跟着变**。
一个"演出来的"页面做不到"跟着你的输入一起变"。

## 方法 6 · 证明「断言有牙」（反向测试）★ 最容易被忽略的一条

**问题**：一条断言写着 PASS，不代表它**能抓到错误**。
比如原来的 E2E 只断言「ID 跨帧稳定」—— **如果跟踪器偷懒输出一个固定不变的框**，
ID 稳定、`area_ratio` 自洽，**照样全 PASS**。

**做法**：故意造一个**错误输入**，断言**必须 FAIL**。

我实测（`test/visual_tracker/e2e_test/`，把假检测源的 `~vx/~vy` 设成 0，即目标每帧原地不动）：

```
########## 反向测试：假目标【固定不动】(vx=0, vy=0) ##########
PASS: area_ratio 与 bbox/(640x480) 一致
PASS: ID 跨帧稳定（全程 id=1，共 50 帧）        ← 旧检查全放过去了
FAIL: 航迹中心几乎没动：跨度仅 0.0 像素 < 100.0
      （固定不变的框也能骗过 ID 稳定检查）      ← 新断言抓出来了
退出码: 1   ✅ 断言有牙
```

**这条暴露的漏洞已修**：`check_tracks.py` 新增 `~check_move` / `~min_move`，
`run_e2e.sh` 阶段A 已启用（要求航迹中心跨度 ≥ 100 像素）。
修完再跑正向：`PASS: 航迹中心确实在移动（跨度 236.0 像素 >= 100.0）`，
`E2E RESULT: PASS (A=0, B=0, C=0)`，单测 `234 passed`。

> **通用教训**：验收别人的东西时，除了"跑通了"，还要问一句
> **「我把输入故意搞坏，它会不会报错？」** —— 不报错的检查等于没有检查。
