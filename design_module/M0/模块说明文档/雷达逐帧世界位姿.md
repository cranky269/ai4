# 雷达逐帧观测机世界位姿

## 接口与数据定义

新增 `/radar/uav_pose_world`，类型 `geometry_msgs/PoseStamped`，非 latched，发布队列长度 2。仅机载 `mounted_radar.launch` 开启；地基 `radar_3d.launch` 不发布观测机位姿，避免把地面传感器冒认为无人机。已有 `/camera_motion_demo/actual_pose` 来自异步 GetModelState，仍保留其原有用途，不能替代逐帧采样位姿。

- `header.stamp`：与对应 `/radar/points.header.stamp` 完全相同的 sec/nsec，直接来自同一 Gazebo `LaserScanStamped.time`，不使用发布时刻最新位置。
- `header.frame_id = world`：当前 Gazebo `base_scene` 世界的固定坐标系，原点是世界 SDF 的 `(0,0,0)`，地面位于 z=0；x/y 是该 SDF 的水平轴，z 向上，右手系。场景没有地理定位，不把 x/y 声称为真实东/北。
- `pose.position.{x,y,z}`：观测模型 `static_uav` 的模型原点，单位米；对应既有 `uav_base_link` 参考点。当前模型的 `base_link` 相对模型位姿为零，因此两者重合。若固定 base_link 偏移非零，仍回算到模型原点，保持 GetModelState/既有 world→uav_base_link 的参考点约定。
- `pose.orientation.{x,y,z,w}`：该机体参考系相对 world 的单位四元数（ROS 顺序 x/y/z/w）；机体轴 x 前、y 左、z 上。不是目标机 `target_uav` 位姿，也不是雷达中心。

`/radar/points` 的消息类型、字段、布局、数值计算、原生时间戳和 `radar_link` 保持原样；点云 XYZ 仍是雷达局部坐标，不因新增世界位姿而变成世界点云。两话题跨 ROS 连接不保证到达次序或原子交付，使用完全相同的时间戳配对，不使用“最近帧”。不依赖 seq 作为跨话题配对键。原记录器话题列表本轮保持原样；若需保存新增接口，可用 rosbag 显式同时记录这两个话题。

## 原始位姿含义与固定安装链

Gazebo Classic 11 `RaySensor::UpdateImpl` 在生成本帧消息时记录仿真采样时间，并将传感器局部 pose 与 parentEntity 的 WorldPose 组合后写入 `scan.world_pose`。它是扫描坐标系的世界位姿，不是无人机原点。

源码依据：[gazebo11 RaySensor.cc](https://github.com/gazebosim/gazebo-classic/blob/gazebo11/gazebo/sensors/RaySensor.cc)，重点 `UpdateImpl`、`lastMeasurementTime` 和 `mutable_world_pose`。

采用齐次变换约定 `T_AB` 将 B 系坐标变换到 A 系：

```
T_model_sensor = T_model_base_link * T_base_link_sensor
T_world_model = T_world_sensor * inverse(T_model_sensor)
```

包含平移和三轴旋转，不能仅按世界轴减去 `(0.30,0,0.12)`。`prepare_mounted_radar.py` 从实际生成模型的 base_link pose 和 ray_3d sensor pose 读取完整固定链，生成本次运行目录的 `radar_pose.yaml`；launch 将它加载到桥接私有参数。默认链为模型→base_link 单位变换、base_link→sensor `(0.30,0,0.12,0,0,0)`。不从目标模型读取变换。不支持的 relative pose 属性、含 joint 的模型或非法固定 pose 明确拒绝，避免默默遗漏中间变换；以后引入复杂 SDF frame graph 必须先扩展解析。

## 函数与调用关系

增量链为 `prepare → radar_pose.yaml → mounted_radar.launch → RayCloudBridge::PublishPose`；现有 OnScan 的点云算法不变，在发布点云前以同一原始消息调用位姿转换。

新增私有参数：`publish_uav_pose` 默认 false，机载 launch 设置 true；`uav_pose_topic` 默认 `/radar/uav_pose_world`；`body_to_sensor` 为模型参考系到扫描系的六元素 `[x,y,z,roll,pitch,yaw]`，单位米/弧度；`scan_parent` 为预期原生父框架 `static_uav::base_link`。后两项必须由生成配置提供，缺失或非有限时启动失败。

`PublishPose(message, stamp)`：输入当前 LaserScanStamped 和当前 cloud 原生时间戳；检查扫描父框架、位姿存在性、有限数值、四元数范数，计算并发布 PoseStamped。无 latest-pose 查询、TF 插值或历史位姿缓存；不读取 `/target/*`。新增成员仅是桥接内部实现，不改既有消息数据结构。

## 缺失与重置

若原始位姿缺失、父框架不符、坐标非有限或四元数范数不合法，本帧保持原点云发布，抑制配对位姿并明确输出 `Radar UAV pose pair missing` 错误。消费者在等待窗口内找不到同时间戳位姿时应标记配对缺失，不能补零或沿用上帧。位姿话题非 latched，避免新订阅者收到过期位置。

扫描时间回退时桥接告警并开始新 epoch。因为每帧位姿都直接从该帧消息计算，没有历史配对缓存，不会把重置前的位姿配到重置后的扫描。ROS 标准 PoseStamped 没有 epoch 字段，因此下游必须在输入消息时间戳回退、`/clock` 回退或重启会话时清空自己的同步队列；本机 Gazebo ROS 时钟在 reset 后可能暂时等待仿真追上旧时间，不能只依赖 `/clock` 检出重置；不要在跨运行的 bag/日志中单独以 sec/nsec 全局去重。两条独立传输连接的边界迟到消息不能单靠 PoseStamped 的时间字段判定运行身份。

## 验证方法

`test/uav_sim/radar_pose/README.md` 记录真实 Gazebo 回归方法。独立 world plugin 逐物理步记录 `static_uav.WorldPose()` 及仿真时间，核验只用完全相同的时间与 epoch，不用发布时刻的最新服务读数替代。测试生成世界中同时设置非零模型→base_link、base_link→sensor 平移及三轴旋转，覆盖平移、转向、roll/pitch 和 reset_simulation。

本次统一入口以 `gui:=false camera_view:=false` 验证数据链，图形界面画面不属于此项验证；详细数量、误差、配对示例及运行产物见桌面 codex结果 本次报告。

## 统一启动的重置看门狗

`start_sensor_clock.py` 保留真实的各路消息年龄；当原生雷达时间戳回退且新采样时间仍小于重置前 `/clock` 时，`startup_health.json.clock_reset_catching_up=true`。只在这个明确区间暂缓单独的 `/clock` 停滞判断，相机和雷达仍须持续更新；当 `/clock` 自身回退或雷达追上旧时刻后恢复完整时钟检查。没有重写 `/clock` 或任何传感器时间戳，也没有把旧位姿当成新位姿。这避免了 Gazebo ROS reset 后暂不发布较小 `/clock` 所造成的 20 秒误报退出。
