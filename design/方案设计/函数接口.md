## 决策端设计原则（讨论定稿）

> 以下原则由主文档推导并经设计讨论定稿，作为各模块「无数据时行为」的统一依据（已同步修订至主文档第八章第 7-9 条）。

### 1. 三层模型与双层兜底

系统分为**采集端**（雷达链 + 视觉链，按传感器固有频率出数据）、**决策端**（状态机 + navigator + pid + mux）、**执行端**（mavros → PX4）。兜底分两层：

- 决策端发的悬停/零速默认指令 = **优雅兜底**（OFFBOARD 不掉，随时可恢复跟踪）；
- PX4 OFFBOARD failsafe（setpoint 断流 >0.5s 切出）= **保命兜底**（决策端时钟全部死亡时的最后防线）。

两层各管各的死法，不可互相替代。

### 2. 决策端固定时钟与「短保持、长默认」

navigator 与 pid **必须以 20-50Hz 定频发布**（OFFBOARD 硬性要求），内容三选一：
当前定义为50Hz


| 输入状态 | 指令内容 |
|---|---|
| 有新数据 | 新指令 |
| 短时无数据（未超时） | 重发上一条（保持） |
| 长时无数据 / 上游故障 | 默认指令（悬停） |

「无数据时长」一律按**距上次非空数据**计时（空数组到达不刷新计时，见第 5 条）——否则「空也发」约定下空数组持续到达会使超时永不到期，业务性丢失将退化为无限期保持旧速度指令（违反第 3 条）。

各决策节点内部统一为**事件层 + 时钟层**结构：事件层（订阅回调）只存最新值并刷新时间戳；时钟层（定时器）做全部内容选择与发布。缺席检测只能住在时钟层——**缺席没有回调**。时钟层入口为各模块的 `on_timer` 总领函数（见 3.4 / 6.4）。

**分工边界**：状态机管**通道选择**（谁说话，经 `/state`→mux），navigator/pid 管**内容生成**（说什么）——默认指令由节点对自身输入的缺席超时**自判触发，不订阅 `/state`、不依赖状态机存活**；两套判断观察同一数据源，时序大致重合但互不依赖。

### 3. 指令类型决定保持的安全边界

- **位置类指令**（雷达链航点）：绝对量，可**无限期**安全保持；
- **速度/角速度类指令**（视觉链伺服）：相对量，只能**有界保持**（超时即转默认指令），无界保持 = 盲目追踪幽灵目标。

因此两条链的默认指令口味不同：navigator 用 `hover_setpoint`（位置保持，订阅位姿回传），pid 用 `stop_setpoint`（速度归零，不订阅位姿）。

### 4. 时钟清单

| 节点 | 时钟 | 说明 |
|---|---|---|
| navigator / pid | 必须（20-50Hz） | 指令流唯一责任人，「短保持、长默认」策略住在这里 |
| state_machine | 无发布时钟 | `/state` 按变化发布；N/M/K 帧计数以数据消息为节拍（见第 5 条，主文档第八章第 7 条） |
| mux | 无 | **事件转发**（收到即转、原样转），指令流连续性由上游保证 |

### 5. 采集端「无内容发空、不静默」约定

数组类话题（`/detections`、`/visual/tracks`、`/radar/centroid`、`/radar/tracks`）无内容时**发布空数组而非静默**，使全链路「空 = 没目标（业务正常）、静默 = 故障」语义成立，同时为状态机帧计数提供节拍。

### 6. 不加指令有效标志位

指令有效性不通过字段传播（`PositionCommand` 为纯数据类型，虽可加字段但约定不加）：缺席检测住在本节点定时器里，判断结果**体现在指令内容上**（悬停/零速可从 setpoint 内容直接辨认），不向上游回传。

## 模块 3：导航（`/navigator`）

> 职责（文档）：航迹 → 航点解算（雷达引导指令）。雷达点云已在数据源（`/radar_sim`）侧转为世界坐标系（world frame），navigator 直接消费世界坐标航迹，不再做「雷达系 → 世界系」变换；真机仍需留意「世界系 → 飞控 local ENU」原点对齐与 ENU/NED 轴差异（第八章第6条、M3）。订阅 `/radar/tracks`，发布 `/ctrl/radar`。
> 另：长时无有效航迹时输出原地悬停 setpoint（第四章注）——由**输入超时自判触发，不订阅 `/state`**（与状态机进入 `SEARCH/RTH` 时序重合但互不依赖）；悬停需当前位置，故另订阅 `/mavros/local_position/pose`（文档推导，即主文档第二章 mavros 行「位姿回传」的消费者）。

> - 深度·逼近段：`compute(期望面积, max(bbox面积, 最小面积), dt)` → body velocity x（面积小于期望 → 误差为正 → 前进）

## 模块 7：控制仲裁（`/control_mux`）

> 职责（文档）：订阅 `/state`、`/ctrl/radar`、`/ctrl/visual`，按状态只放行一路，转发到 `/mavros/setpoint_raw/local`，其余丢弃。唯一向飞控发指令的出口。原则「只转发不生成」。
>
> 指令类型说明：mux 为纯转发节点，直接透传 ROS 消息 `mavros_msgs/PositionTarget`（不生成、不解释指令内容），故其纯逻辑将指令视为**不透明载荷**，不涉及 `PositionCommand`（后者仅存在于 navigator / pid 的纯逻辑侧）。

### 7.1 `select_channel`（文档推导，源自第三章 3.7 仲裁规则）

```python
def select_channel(state: str) -> str
```

| 项目 | 说明 |
|---|---|
| 输入 | `state`：最近一次收到的状态值（`RADAR_GUIDE` / `VISUAL_LOCK` / 其他） |
| 输出 | `str`：放行通道（`"/ctrl/radar"` 或 `"/ctrl/visual"`） |
| 作用 | 按仲裁规则选择放行通道：`RADAR_GUIDE`→雷达，`VISUAL_LOCK`→视觉，其他值→回退雷达 |

> 设计取舍（方案 B，详见主文档第八章第 8 条）：**不做 `/state` 超时检测**，安全性由 `stop_setpoint` + PX4 OFFBOARD failsafe 两层兜底（代价：状态机挂死时飞机卡在视觉通道安全悬停；后期可纯增量补 `state_age`）；mux 为**事件转发**（无定时器），流连续性由上游固定时钟保证（设计原则第 4 条）。

> 仲裁规则表（文档 3.7，已按方案 B 修订）：
> | `/state` 值 | 放行 |
> |---|---|
> | `RADAR_GUIDE` | `/ctrl/radar` |
> | `VISUAL_LOCK` | `/ctrl/visual` |
> | 其他值（含 `SEARCH/RTH`） | `/ctrl/radar`（回退） |

**第九章优化备注**：第九章第2条「切换瞬间平滑」——`RADAR_GUIDE → VISUAL_LOCK` 硬切可能指令突变抖动；若硬切不达标，在 mux 内对切换前后指令做限幅/一阶低通平滑（可选）。

## 模块 8：状态机（`/state_machine`）

> 职责（文档）：雷达/视觉切换 + 熔断。订阅 `/detections` `/visual/tracks` `/radar/tracks`，发布 `/state`。三态：`RADAR_GUIDE` / `VISUAL_LOCK` / `SEARCH/RTH`。
> 本章函数由第四章「量化切换条件」推导（文档未给签名）。

### 8.1 `evaluate_visual_lock`（文档推导，源自第四章视觉锁定进入条件）

```python
def evaluate_visual_lock(detections: list[DetectedTarget], visual_tracks: list[VisualTrack], conf_thresh: float = 0.8, area_thresh: float = 0.02) -> bool
```

| 项目 | 说明 |
|---|---|
| 输入 | `detections`：检测结果；`visual_tracks`：视觉航迹（来自 `VisualTrackArray` 解包）；`conf_thresh`：置信度阈值（默认 0.8 = 80%）；`area_thresh`：面积比阈值（默认 0.02 = 2%） |
| 输出 | `bool`：是否满足视觉锁定条件 |
| 作用 | 判断当前帧是否满足「置信度 > 阈值 且 BBox 面积 > 阈值」的视觉锁定进入条件 |

### 8.2 `evaluate_radar_lost`（文档推导，源自第四章 SEARCH/RTH 进入条件）

```python
def evaluate_radar_lost(radar_tracks: list[Track]) -> bool
```

| 项目 | 说明 |
|---|---|
| 输入 | `radar_tracks`：雷达航迹列表（纯类型 `Track` 数组，节点壳由 `/radar/tracks` 的 `TrackArray` 拆包） |
| 输出 | `bool`：`True` 表示雷达无有效航迹（丢失） |
| 作用 | 判断当前帧雷达是否丢失（用于进入/退出 `SEARCH/RTH`） |

### 8.3 `transition`（文档推导，源自第四章状态转移规则）

```python
def transition(state: str, visual_lock: bool, radar_lost: bool, counters: dict) -> str
```

| 项目 | 说明 |
|---|---|
| 输入 | `state`：当前状态；`visual_lock`：视觉锁定条件；`radar_lost`：雷达丢失标志；`counters`：N/M/K 连续帧计数器 |
| 输出 | `str`：新状态 |
| 作用 | 按第四章状态机规则执行状态转移（含「连续 N 帧保持」「连续 M 帧丢失」「连续 K 帧无航迹」计数判定） |

> 切换规则（文档第四章）：
> - 进入 `VISUAL_LOCK`：视觉锁定条件连续 N 帧保持
> - 退出 `VISUAL_LOCK`：连续 M 帧丢失目标 → `RADAR_GUIDE`
> - 进入 `SEARCH/RTH`：`RADAR_GUIDE` 下连续 K 帧无雷达航迹
> - 退出 `SEARCH/RTH`：雷达恢复航迹 → `RADAR_GUIDE`
> - **优先级**：`RADAR_GUIDE` 下视觉锁定与雷达丢失同时成立时，**视觉锁定优先**（进入 `VISUAL_LOCK`）；该优先级不外延到 `SEARCH/RTH`——`SEARCH/RTH` 仍只由「雷达恢复航迹」退出。

> **实现补充（节拍落地，方案 B）**：状态机**无发布时钟**（设计原则第 4 条），其「帧」由**数据到达**定义。rospy 为事件驱动——每个订阅回调独立触发、由单线程 spinner 串行执行，故「以哪一路为节拍」取决于**推进调用写在哪一路的回调里**。落地约定：
>
> - **以 `/detections` 为唯一节拍**：三路回调各自刷新本路缓存，其中 `/visual/tracks`、`/radar/tracks` **仅刷新缓存、不推进**，**只有 `/detections` 到达才推进一步**（调 `transition`）——于是「收到一条 `/detections`」= 「走一拍」；
> - **计数单位**：`N/M/K` 以「`/detections` 帧数」计，语义稳定，不受各路频率差影响，也避免「同一相机帧被 `/detections` 与 `/visual/tracks` 各计一次」；
> - **缓存判定**：每拍用三路**缓存的最新值**（而非「本拍到了什么」）判定，故某路较慢时不会因「本拍未到」被误判为空；
> - **发布**：`/state` 按变化发布（启动先发一次初值）；
> - **换节拍**：改主节拍只需把推进调用移到另一路回调；若改用时钟节拍（`rospy.Timer`）即前述方案 C。

**第九章优化备注**：无。
